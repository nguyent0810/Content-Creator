# 07 Production Engine: Permanent Production Operating System for the Buddhist AI Studio

## Document Control

**Document Type:** Permanent Production Operating System  
**Governing Specifications:** `PROJECT_PRD.md`, `01_BRAND_BIBLE.md`, `02_BUDDHIST_GUIDE.md`, `03_CONTENT_ARCHITECTURE.md`, `04_CONTENT_ENGINE.md`, `05_RESEARCH_ENGINE.md`, and `06_VISUAL_ENGINE.md`  
**Primary Function:** Central orchestration layer for transforming approved requests into complete publication-ready production packages  
**Operating Boundary:** The Production Engine coordinates specialized engines. It does not research, write, design, generate prompts, create thumbnails, or publish independently without approved inputs and gates.  
**Supported Outputs:** Long video packages, Shorts packages, podcast packages, community post packages, article packages, course material packages, visual package records, publishing packages, analytics reports, archive packages, and future format packages  
**Longevity Target:** 10+ years of scalable, modular, observable, traceable, auditable Buddhist media production  
**Permanent Standard:** Quality before quantity, consistency before speed, systems before individuals, traceability before convenience, and Buddhist integrity before platform performance

## Operating Premise

The Production Engine is the studio's orchestration system. It does not replace the Research Engine, Content Engine, Visual Engine, Buddhist Guide, Brand Bible, Content Architecture, or PRD. It coordinates them. Its job is to make sure that every content request passes through the correct engines in the correct order, produces the correct artifacts, receives the correct reviews, and enters the archive with clear lineage.

The Production Engine exists because a professional AI-powered Buddhist media studio cannot rely on individual memory, improvised workflows, or one all-purpose AI agent. Research, planning, writing, visual design, metadata, review, publishing, analytics, and archiving are different functions. Each requires different inputs, standards, risks, and outputs. The Production Engine turns those functions into a coherent operating system.

The Production Engine never asks, "Can we make this quickly?" before asking, "Can we make this responsibly?" It coordinates speed only after quality gates are defined. It treats every asset as part of a long-term Buddhist library, not as an isolated upload. It assumes that every production choice has future consequences: source traceability, doctrinal consistency, visual trust, metadata retrieval, playlist continuity, and viewer safety.

The operating question is:

**Has every required specialized engine completed its work, produced the required artifact, passed the required gate, and preserved the asset's lineage?**

If the answer is no, production must not proceed.

# PART 1 - Production Philosophy

## Why Production Exists

Production exists to transform approved knowledge, strategy, and creative intent into publishable assets without losing quality, integrity, or traceability. In this studio, production is not merely task management. It is the discipline that protects the channel's spiritual, editorial, visual, and research standards as content moves through many hands and AI systems.

Production is the bridge between idea and public trust. A good idea can fail if research is incomplete, a script exceeds the evidence, a thumbnail distorts the tone, metadata is missing, a review is skipped, or the archive loses version history. The Production Engine prevents these failures by coordinating every stage.

Production exists to make quality repeatable. A single excellent video can happen through talent. A thousand trustworthy assets require systems. The studio must be able to produce consistent Buddhist content even when team members change, AI models change, platforms change, formats multiply, and the library expands.

Production also exists to protect boundaries. The Production Engine ensures that research does not become content without handoff, content does not invent claims, visuals do not exceed doctrine, SEO does not distort the promise, and analytics do not override ethics.

## Quality Before Quantity

The studio must never increase volume by weakening research, doctrinal review, visual QA, accessibility, or archive discipline. Quantity is valuable only when the system can preserve quality at scale.

Quality before quantity means:

**No content without a Knowledge Packet where required.**

**No high-risk topic without escalation.**

**No visual asset without QA.**

**No publishing package without metadata.**

**No platform optimization that violates brand or Buddhist integrity.**

**No production shortcut that breaks traceability.**

If production capacity is limited, reduce output. Do not reduce standards. The channel's long-term credibility is more valuable than any short-term schedule.

## Consistency Before Speed

Consistency is the viewer's experience of trust over time. It appears in terminology, tone, visual identity, playlist placement, citation behavior, emotional safety, and community posture. Speed can help only when consistency is preserved.

Consistency before speed means:

**Use the same source hierarchy.**

**Use the same glossary.**

**Use the same claim classification.**

**Use the same visual dignity rules.**

**Use the same metadata schema.**

**Use the same review gates.**

**Use the same archive lineage.**

If a task is urgent but cannot pass the consistency checks, it is not ready. Urgency does not create permission to bypass the system.

## Systems Before Individuals

The studio should not depend on one person or one AI model remembering everything. A professional production system externalizes knowledge into documents, artifacts, metadata, version records, source registries, visual bibles, checklists, and approval logs.

Systems before individuals means:

**Roles are defined.**

**Inputs and outputs are explicit.**

**Artifacts have schemas.**

**Decisions are recorded.**

**Failures have recovery protocols.**

**Archives preserve lineage.**

**AI agents operate within contracts.**

Individuals may bring taste and judgment, but the system preserves continuity.

## Repeatability

Repeatability means the studio can take a new approved request and reliably move it through research, planning, content, visuals, review, publishing, analytics, and archive without improvising the process every time.

Repeatability requires:

**Stage definitions**

**Gate criteria**

**Artifact schemas**

**Agent responsibilities**

**Version naming**

**Escalation rules**

**Feedback loops**

Repeatability does not mean formulaic content. It means the process is stable while the creative result remains tailored.

## Traceability

Traceability means every published asset can be traced backward to its research, knowledge packet, planning brief, content decisions, visual decisions, reviews, approvals, metadata, publishing package, analytics, and archive record.

Traceability protects the studio when:

**A viewer questions a claim.**

**A reviewer identifies an error.**

**An asset must be updated.**

**A series needs revision.**

**AI agents need prior context.**

**A source is deprecated.**

**A visual is replaced.**

Without traceability, the library becomes fragile. With traceability, it can mature.

## Long-term Maintainability

Maintainability means the studio can update, repair, reuse, expand, and archive assets without losing context. A production system that only publishes but cannot maintain will eventually decay.

Maintainability requires:

**Asset lineage**

**Version control**

**Source mapping**

**Metadata completeness**

**Archive status**

**Replacement rules**

**Correction memory**

**Analytics feedback**

Every asset should be born maintainable.

# PART 2 - Studio Architecture

## Overview

The studio architecture is divided into layers. Each layer has a distinct responsibility and output. The Production Engine coordinates the movement between layers but does not merge them.

The permanent layers are:

**Knowledge Layer**

**Research Layer**

**Planning Layer**

**Content Layer**

**Visual Layer**

**Review Layer**

**Publishing Layer**

**Analytics Layer**

**Archive Layer**

Each layer must be modular, replaceable, observable, traceable, auditable, scalable, and future-proof.

## Knowledge Layer

**Responsibility:** Preserve the studio's long-term knowledge system: governing documents, glossary, Knowledge Graph, content architecture, source registry, dossiers, concept anchors, and correction memory.

**Inputs:** Governing documents, approved Knowledge Packets, source records, glossary updates, viewer confusion logs, correction records, archive metadata.

**Outputs:** Canonical definitions, concept nodes, taxonomy paths, approved terminology, related asset mappings, knowledge lineage, update alerts.

**Limits:** The Knowledge Layer does not create content. It preserves and organizes knowledge.

**Production role:** The Production Engine queries the Knowledge Layer before planning, during metadata validation, and after analytics feedback.

## Research Layer

**Responsibility:** Produce evidence-based, confidence-scored Knowledge Packets through the Research Engine.

**Inputs:** Research request, core question, topic scope, risk flags, source registry, dossiers, prior packets.

**Outputs:** Research Dossier, Knowledge Packet, source list, evidence matrix, confidence table, approved claims, risk flags, escalation notes.

**Limits:** The Research Layer does not write scripts, design visuals, or optimize packaging. It defines what can responsibly be said.

**Production role:** Production cannot proceed to content planning until the Research Gate is passed or an approved low-risk exception is documented.

## Planning Layer

**Responsibility:** Convert approved research and architecture mapping into an asset plan.

**Inputs:** Knowledge Packet, Content Architecture, viewer journey stage, series brief, format request, production constraints.

**Outputs:** Episode Brief or Asset Brief, format decision, audience state, learning goal, content function, dependencies, required artifacts, production schedule.

**Limits:** The Planning Layer does not write the final content. It defines the task.

**Production role:** The Production Engine validates that planning aligns with the library and avoids duplication.

## Content Layer

**Responsibility:** Transform the approved brief and Knowledge Packet into content artifacts according to the Content Engine.

**Inputs:** Knowledge Packet, Asset Brief, format requirements, brand voice rules, Buddhist Guide, Content Engine.

**Outputs:** Story Outline, Audio Script, article draft, podcast draft, community post draft, course draft, newsletter draft, or other content artifact.

**Limits:** The Content Layer may not introduce unsupported claims. It may not exceed the Knowledge Packet.

**Production role:** The Production Engine sends content outputs to review gates and revision cycles.

## Visual Layer

**Responsibility:** Create visual planning and visual asset instructions according to the Visual Engine.

**Inputs:** Asset Brief, approved content artifact, Visual Engine, series visual bible, Visual Research Packet, accessibility requirements.

**Outputs:** Visual Brief, Thumbnail Brief, image generation package specification, motion notes, editing notes, visual QA record.

**Limits:** The Visual Layer does not create doctrine. It may not visually imply claims not supported by research or content.

**Production role:** The Production Engine ensures visual planning is synchronized with content and reviewed before publishing.

## Review Layer

**Responsibility:** Evaluate research, content, visuals, metadata, SEO, safety, accessibility, doctrinal accuracy, and publishing readiness.

**Inputs:** All stage artifacts.

**Outputs:** Review notes, pass or fail decisions, conditional approval, escalation decisions, revision requests, final approval.

**Limits:** The Review Layer does not silently rewrite history or override evidence. It requests corrections through proper stages.

**Production role:** The Production Engine enforces mandatory gates and prevents unapproved assets from advancing.

## Publishing Layer

**Responsibility:** Assemble approved assets into final platform-specific publishing packages.

**Inputs:** Approved content, approved visuals, approved metadata, SEO package, references, playlist assignments, cross-links, publishing schedule.

**Outputs:** Publishing Package, platform upload checklist, description, tags, pinned comment, references, playlist mapping, distribution plan.

**Limits:** The Publishing Layer may not alter claims, tone, visuals, or titles beyond approved scope.

**Production role:** The Production Engine validates package completeness and publishing gate approval.

## Analytics Layer

**Responsibility:** Observe performance, viewer behavior, feedback, retention, CTR, search, comments, and learning signals.

**Inputs:** Published asset data, comments, retention curves, search queries, playlist movement, viewer feedback, community responses.

**Outputs:** Analytics Report, viewer confusion log, performance notes, update recommendations, content gaps, visual feedback, metadata improvement suggestions.

**Limits:** Analytics may recommend changes but cannot override doctrine, brand, research, or safety.

**Production role:** The Production Engine routes analytics into Knowledge Feedback and archive updates.

## Archive Layer

**Responsibility:** Preserve asset lineage, versions, source connections, approvals, metadata, publishing records, analytics, and update history.

**Inputs:** All final artifacts, approvals, source records, version notes, analytics reports, corrections, replacement decisions.

**Outputs:** Archive Package, asset lineage, version history, reuse permissions, deprecation records, replacement mapping.

**Limits:** The Archive Layer does not change content. It records and governs asset state.

**Production role:** No asset is complete until archived.

## Lifecycle Overview

The complete lifecycle is:

**Idea**

**Research Request**

**Knowledge Packet**

**Content Creation**

**Visual Planning**

**Asset Creation**

**Review**

**Revision**

**Approval**

## Idea

An idea is a raw production possibility. It may come from the content architecture, viewer feedback, seasonal planning, research gap, series roadmap, analytics, or human editorial direction.

The idea stage must capture:

**Raw request**

**Intended format if known**

**Viewer need**

**Potential pillar**

**Potential risk**

**Reason for consideration**

An idea is not approved content. It must not move directly to writing.

## Research Request

The Research Request converts the idea into a researchable question. It defines scope, claim type, source requirements, and risk flags.

Required fields:

**Core research question**

**Topic boundary**

**Tradition context**

**Expected claim types**

**Sensitivity flags**

**Needed sources**

**Escalation triggers**

The Production Engine routes the request to the Research Agent and blocks content creation until research is complete.

## Knowledge Packet

The Knowledge Packet is the approved research output. It defines what may be said, what must be qualified, what must be omitted, and what risks apply.

The Production Engine validates:

**Packet completeness**

**Confidence scoring**

**Source traceability**

**Risk flags**

**Approved claim table**

**Escalation resolution**

If incomplete, the packet returns to research.

## Content Planning

Content Planning turns the Knowledge Packet into an asset plan. It uses the Content Architecture to place the asset and the Content Engine to define its experience.

Planning defines:

**Asset function**

**Format**

**Learning goal**

**Viewer promise**

**Core question**

**Core insight**

**Viewer journey stage**

**Concept nodes**

**Dependencies**

**Related assets**

**Required content artifact**

If the planned asset duplicates existing content, the Production Engine must stop or redirect.

## Content Creation

Content Creation produces the draft artifact. This may be a story outline, audio script, article draft, newsletter draft, podcast plan, community post draft, course lesson draft, or other approved artifact.

The Content Layer must use only approved research and must follow voice, tone, safety, and format rules. It may request additional research if a gap appears.

The Production Engine tracks versioning from first draft onward.

## Visual Planning

Visual Planning defines how the asset should be seen. It does not create final visuals yet. It produces briefs and specifications.

Visual Planning includes:

**Visual intent**

**Scene or asset list**

**Character requirements**

**Environment requirements**

**Symbol use**

**Palette**

**Lighting**

**Thumbnail direction**

**Motion needs**

**Accessibility notes**

**Visual risk flags**

If sacred figures, historical settings, or sensitive topics appear, Visual Planning must request visual research or review.

## Asset Creation

Asset Creation produces concrete production components according to approved briefs. This may include audio recording, visual assets, editing sequences, motion graphics, captions, metadata, SEO assets, or platform packages.

The Production Engine coordinates asset creation but does not allow assets to bypass review. Every produced asset must preserve its source brief and version identity.

## Review

Review checks each artifact against its relevant governing engine.

Review types:

**Research review**

**Editorial review**

**Doctrinal review**

**Safety review**

**Visual review**

**Accessibility review**

**SEO and metadata review**

**Publishing review**

High-risk content requires elevated review. Review results are recorded as pass, conditional pass, fail, or escalate.

## Revision

Revision addresses review notes. It must be controlled. A revision cannot introduce new claims or visual meanings outside approved research and briefs.

Revision must record:

**Change reason**

**Changed artifact**

**Version number**

**Reviewer request**

**Resolution**

If revision creates new research questions, the asset returns to the Research Layer.

## Approval

Approval confirms that all required gates have passed and artifacts are ready for package assembly. Approval is role-specific. A visual approval does not approve doctrine. A research approval does not approve final publishing.

Final approval requires:

**Research approved**

**Content approved**

**Visuals approved**

**Metadata approved**

**SEO approved**

**Publishing package approved**

**Archive readiness confirmed**

## Publishing Package

The Publishing Package contains everything needed for distribution. It must be complete, versioned, and platform-specific.

Required package elements depend on format but may include:

**Final media**

**Title**

**Description**

**Thumbnail**

**Tags**

**Pinned comment**

**References**

**Playlist assignment**

**Cross-links**

**Captions**

**Metadata**

**Accessibility notes**

**Archive links**

## Distribution

Distribution publishes approved packages to platforms. Distribution must not modify core assets without approval. If platform constraints require changes, the change must be logged and, if meaningful, reviewed.

Distribution includes:

**Scheduling**

**Upload**

**Playlist placement**

**Cross-link activation**

**Community announcement if approved**

**Website or newsletter linkage if relevant**

## Analytics

Analytics observes how the asset performs and how viewers respond. Analytics should measure both platform performance and trust indicators.

Analytics includes:

**Retention**

**CTR**

**Search traffic**

**Suggested traffic**

**Comments**

**Shares**

**Playlist progression**

**Viewer confusion**

**Sentiment**

**Evergreen performance**

Analytics does not dictate doctrine. It informs improvement.

## Knowledge Feedback

Knowledge Feedback routes analytics and viewer response back to the Knowledge Layer, Content Architecture, Research Engine, Content Engine, and Visual Engine.

Feedback may trigger:

**Glossary clarification**

**Metadata updates**

**Playlist changes**

**Visual revisions**

**Content corrections**

**New research**

**Archive status changes**

This closes the production loop.

# PART 4 - Production Agents

## Agent System Philosophy

Production agents are specialized roles. They may be AI agents, human roles, or hybrid workflows. Each agent has a mission, inputs, outputs, limits, escalation rules, and failure conditions. The Production Engine coordinates agents but does not collapse them into one general assistant.

## Research Agent

**Mission:** Produce evidence-based research artifacts through the Research Engine.

**Inputs:** Research Request, source registry, dossiers, prior Knowledge Packets, risk flags.

**Outputs:** Research Dossier, Knowledge Packet, evidence matrix, confidence table, source list, risk notes.

**Responsibilities:** Search appropriate sources, classify claims, detect conflicts, score confidence, flag escalation, prevent hallucination.

**Limits:** Does not write scripts, design visuals, create publishing copy, or approve high-risk content alone.

**Escalation Rules:** Escalate for translation issues, doctrinal conflict, high-risk sensitive topics, uncertain sources, or insufficient evidence.

**Failure Conditions:** Fake citations, unverified quotes, missing confidence scores, weak source reliance, tradition collapse, unsupported claims.

## Planner Agent

**Mission:** Convert approved research into a production-ready plan aligned with the Content Architecture.

**Inputs:** Knowledge Packet, content architecture, series brief, viewer journey, production request.

**Outputs:** Asset Brief, format decision, dependency map, production requirements, metadata draft.

**Responsibilities:** Determine asset function, avoid duplication, map pillars and concept nodes, define learning goal, identify required artifacts.

**Limits:** Does not write final content or invent research.

**Escalation Rules:** Escalate if no series fit exists, topic overlaps existing content, or asset scope is too large.

**Failure Conditions:** Vague brief, missing metadata, duplicate asset plan, unsupported format selection, unassigned risk.

## Writer Agent

**Mission:** Produce approved written content artifacts from the Knowledge Packet and Asset Brief.

**Inputs:** Knowledge Packet, Asset Brief, Content Engine, Brand Bible, Buddhist Guide, format requirements.

**Outputs:** Audio Script, article draft, newsletter draft, community post draft, course draft, podcast draft, or other approved text artifact.

**Responsibilities:** Use approved claims, preserve voice, structure content, avoid forbidden language, maintain format rules.

**Limits:** Does not add claims outside the Knowledge Packet. Does not self-approve doctrine.

**Escalation Rules:** Request research if a needed claim is absent. Escalate if sensitive language cannot be made safe.

**Failure Conditions:** Unsupported claims, AI-pattern writing, fear language, doctrinal drift, tone drift, scope creep.

## Story Agent

**Mission:** Shape narrative structure, emotional progression, story beats, callbacks, and payoffs without distorting truth.

**Inputs:** Knowledge Packet, Asset Brief, Content Engine, approved story sources.

**Outputs:** Story Outline, narrative beat map, emotional arc, retention-safe structure notes.

**Responsibilities:** Build ethical curiosity, organize story movement, prevent fatigue, ensure story serves teaching.

**Limits:** Does not invent sacred dialogue, historical scenes, or scriptural material.

**Escalation Rules:** Escalate if a story source is unclear, legendary material risks being treated as history, or emotional arc becomes manipulative.

**Failure Conditions:** Fabricated narrative, melodrama, fear-based suspense, doctrinal distortion, unresolved open loops.

## Visual Agent

**Mission:** Produce visual planning artifacts according to the Visual Engine.

**Inputs:** Asset Brief, content artifact, Visual Engine, series visual bible, visual research packet.

**Outputs:** Visual Brief, scene list, style guide notes, motion notes, accessibility notes, visual risk flags.

**Responsibilities:** Define visual language, ensure brand alignment, map scenes, protect sacred dignity, identify research needs.

**Limits:** Does not generate final image prompts in this operating role. Does not make doctrinal claims visually.

**Escalation Rules:** Escalate for sacred figures, historical settings, hell imagery, grief, illness, ritual, or cultural specificity.

**Failure Conditions:** Decorative Buddhism, fantasy drift, fear visuals, missing visual research, inaccessible design.

## Thumbnail Agent

**Mission:** Produce thumbnail planning artifacts that attract attention ethically.

**Inputs:** Asset Brief, approved content, Visual Engine, Brand Bible, thumbnail family rules.

**Outputs:** Thumbnail Brief, visual hierarchy plan, text-safe area, emotional framing, risk check.

**Responsibilities:** Define thumbnail purpose, avoid clickbait, preserve dignity, support discoverability, align with series family.

**Limits:** Does not create final thumbnail asset in the Production Engine definition. Does not use fear, miracle, guilt, or secret tactics.

**Escalation Rules:** Escalate for karma, death, hell, grief, medical, filial piety, sacred figures, or high-risk visuals.

**Failure Conditions:** Fear-based CTR, misleading promise, sacred figure misuse, unreadable text, visual mismatch.

## SEO Agent

**Mission:** Create search and discovery strategy without distorting content.

**Inputs:** Asset Brief, approved content, Content Architecture, keyword research if approved, Brand Bible, Buddhist Guide.

**Outputs:** SEO Package, title candidates, description guidance, tags, search intent map, playlist and cross-link suggestions.

**Responsibilities:** Improve discoverability, align with viewer intent, preserve ethical language, avoid clickbait.

**Limits:** Does not change doctrine, promise results, or override approved title ethics.

**Escalation Rules:** Escalate if search demand favors forbidden language, fear framing, or miracle claims.

**Failure Conditions:** Clickbait, misleading metadata, fear keywords, unsupported claims, generic self-help positioning.

## Metadata Agent

**Mission:** Ensure every asset is findable, traceable, and integrated into the library.

**Inputs:** Asset Brief, Knowledge Packet, Content Architecture, publishing package.

**Outputs:** Metadata record, taxonomy path, concept nodes, risk flags, related links, archive metadata.

**Responsibilities:** Complete metadata schema, assign pillars, map concepts, preserve lineage, connect related assets.

**Limits:** Does not decide doctrine or content direction.

**Escalation Rules:** Escalate if asset cannot be categorized, duplicates existing content, or lacks required lineage.

**Failure Conditions:** Missing metadata, wrong taxonomy, orphan asset, broken relationships, incomplete risk flags.

## Reviewer Agent

**Mission:** Evaluate artifacts against governing standards and route issues to the proper layer.

**Inputs:** Stage artifact, governing documents, quality gate criteria, risk profile.

**Outputs:** Review Report, pass, conditional pass, fail, escalation note, revision request.

**Responsibilities:** Check alignment, identify risks, enforce gates, prevent drift.

**Limits:** Does not silently rewrite without version tracking. Does not approve outside authority.

**Escalation Rules:** Escalate high-risk doctrinal, safety, visual, historical, or translation concerns.

**Failure Conditions:** Superficial review, missed unsupported claims, missed unsafe language, untracked changes.

## QA Agent

**Mission:** Perform systematic quality assurance across artifacts and packages.

**Inputs:** All production artifacts, QA checklists, package requirements.

**Outputs:** QA Report, defect list, readiness status, regression check, final gate recommendation.

**Responsibilities:** Verify completeness, consistency, links, references, captions, accessibility, metadata, visual artifacts, and version match.

**Limits:** Does not make creative decisions except defect identification.

**Escalation Rules:** Escalate blocking defects, broken references, mismatched versions, or missing approvals.

**Failure Conditions:** Passing incomplete packages, ignoring defects, failing to retest after revision.

## Publishing Agent

**Mission:** Assemble and execute approved publishing package according to platform requirements.

**Inputs:** Approved final assets, SEO Package, metadata, schedule, playlist assignments, references.

**Outputs:** Published asset record, upload confirmation, distribution checklist, initial monitoring notes.

**Responsibilities:** Upload, schedule, place in playlists, verify descriptions, activate links, preserve version.

**Limits:** Does not alter approved content or thumbnails without review.

**Escalation Rules:** Escalate platform constraints, upload errors, broken captions, incorrect metadata, or asset mismatch.

**Failure Conditions:** Wrong file, wrong title, broken links, missing references, unapproved edits, wrong playlist.

## Archive Agent

**Mission:** Preserve production lineage and asset state after approval and publication.

**Inputs:** Final artifacts, approvals, source links, metadata, publishing record, version history.

**Outputs:** Archive Package, lineage record, reuse status, deprecation status, future retrieval tags.

**Responsibilities:** Store assets, maintain version history, connect knowledge lineage, track reuse rights, record updates.

**Limits:** Does not rewrite content.

**Escalation Rules:** Escalate missing lineage, unclear rights, version conflicts, or unarchived source artifacts.

**Failure Conditions:** Lost files, missing version history, untraceable content, broken archive status.

## Knowledge Agent

**Mission:** Maintain the studio's long-term knowledge system and feed learning back into future production.

**Inputs:** Knowledge Packets, analytics, viewer confusion logs, corrections, archive metadata.

**Outputs:** Glossary updates, concept node updates, knowledge graph updates, content gap alerts, correction memory.

**Responsibilities:** Preserve knowledge continuity, prevent repeated errors, update architecture, maintain concept anchors.

**Limits:** Does not publish or produce public content directly.

**Escalation Rules:** Escalate contradiction, outdated sources, glossary drift, or repeated viewer confusion.

**Failure Conditions:** Knowledge drift, missing correction memory, outdated concept nodes, repeated inconsistencies.

# PART 5 - Input / Output Contracts

## Contract Philosophy

Input and output contracts prevent ambiguity between agents. Every stage accepts specific inputs, validates them, and produces specific outputs. If an input is incomplete, the stage cannot proceed. If an output lacks required metadata, it cannot pass to the next stage.

Contracts are the studio's immune system against chaos.

## Idea Intake Contract

**Accepted Inputs:** Raw request, viewer question, seasonal need, analytics insight, content gap, series roadmap item.

**Required Metadata:** Request source, date, requester, provisional pillar, potential risk, intended format if known.

**Validation Rules:** Must not be a script request bypassing research. Must not ask for forbidden content. Must identify a viewer or library need.

**Expected Output:** Research Request or rejection note.

**Quality Gate:** Idea is scoped enough for research planning.

**Dependencies:** Content Architecture and governing policies.

**Versioning:** Idea ID assigned.

## Research Request Contract

**Accepted Inputs:** Approved idea, core topic, initial scope, risk flags.

**Required Metadata:** Research question, source needs, tradition context, claim types, sensitivity flags.

**Validation Rules:** Must be answerable. Must not be too broad. Must identify high-risk areas.

**Expected Output:** Research task for Research Agent.

**Quality Gate:** Research Plan approved.

**Dependencies:** Research Engine.

**Versioning:** Research Request ID linked to Idea ID.

## Knowledge Packet Contract

**Accepted Inputs:** Completed research, source records, evidence matrix, confidence table.

**Required Metadata:** Topic, core question, definitions, sources, contexts, related concepts, confidence levels, citation requirements, risk flags, escalation status.

**Validation Rules:** Must contain traceable claims. Must classify sources. Must resolve or document conflicts. Must identify approved and prohibited wording.

**Expected Output:** Approved Knowledge Packet.

**Quality Gate:** Research Gate.

**Dependencies:** Source registry, Research Engine, Buddhist Guide.

**Versioning:** Packet version number.

## Asset Brief Contract

**Accepted Inputs:** Knowledge Packet, content architecture mapping, series brief, format decision.

**Required Metadata:** Primary pillar, series, viewer journey stage, asset function, learning goal, viewer promise, risk level, concept nodes, dependencies.

**Validation Rules:** Must not duplicate existing asset unless function differs. Must align with architecture.

**Expected Output:** Asset Brief.

**Quality Gate:** Planning Gate.

**Dependencies:** Content Architecture and Content Engine.

**Versioning:** Brief version linked to Packet ID.

## Content Artifact Contract

**Accepted Inputs:** Asset Brief, Knowledge Packet, format requirements.

**Required Metadata:** Draft version, claims used, sections, format, voice notes, unresolved questions.

**Validation Rules:** Must not introduce unsupported claims. Must obey tone, Buddhist safety, and format rules.

**Expected Output:** Draft content artifact.

**Quality Gate:** Content Gate.

**Dependencies:** Content Engine, Brand Bible, Buddhist Guide.

**Versioning:** Draft version history.

## Visual Brief Contract

**Accepted Inputs:** Asset Brief, approved content direction, visual requirements, series visual bible.

**Required Metadata:** Subject, emotion, palette, lighting, composition, character requirements, environment, symbols, accessibility, risk flags.

**Validation Rules:** Must align with Visual Engine. Must identify sacred or high-risk imagery. Must not imply unsupported claims.

**Expected Output:** Visual Brief or Thumbnail Brief.

**Quality Gate:** Visual Planning Gate.

**Dependencies:** Visual Engine and Content Artifact.

**Versioning:** Visual Brief version.

## Review Contract

**Accepted Inputs:** Stage artifact and gate criteria.

**Required Metadata:** Reviewer, date, artifact version, risk level, decision, issues, required revisions.

**Validation Rules:** Review must match artifact type and authority. High-risk topics require appropriate reviewer.

**Expected Output:** Review Report.

**Quality Gate:** Pass, conditional pass, fail, or escalation.

**Dependencies:** Governing documents.

**Versioning:** Review tied to artifact version.

## Publishing Package Contract

**Accepted Inputs:** Approved final assets, SEO package, metadata, references, playlist assignments.

**Required Metadata:** Platform, asset files, title, description, thumbnail, tags, pinned comment, captions, references, cross-links, schedule, archive ID.

**Validation Rules:** All assets must be final approved versions. Links must work. Metadata must match content. References must be complete.

**Expected Output:** Publishing Package.

**Quality Gate:** Publishing Gate.

**Dependencies:** All prior approvals.

**Versioning:** Package version.

## Archive Package Contract

**Accepted Inputs:** Final published asset, all artifacts, approvals, analytics baseline, metadata.

**Required Metadata:** Asset lineage, version history, source lineage, visual lineage, publishing record, reuse status, maintenance status.

**Validation Rules:** Must allow future reconstruction of production history.

**Expected Output:** Archive Package.

**Quality Gate:** Archive Gate.

**Dependencies:** Publishing Package.

**Versioning:** Archive version and asset status.

# PART 6 - Production Artifacts

## Artifact Philosophy

Artifacts are the studio's memory. Every artifact must have a purpose, owner, schema, quality standard, and lifecycle. Artifacts should be structured enough for AI retrieval and human review.

## Research Dossier

**Purpose:** Support long-term research for major topics, scriptures, concepts, figures, practices, or sensitive domains.

**Owner:** Research Agent and Research Lead.

**Schema:** Scope, exclusions, source list, translation notes, terminology, themes, conflicts, risk notes, citation bank, related dossiers, version history.

**Quality Standard:** Source-ranked, searchable, confidence-aware, maintained.

**Lifecycle:** Created for major domains, updated through audits, deprecated only with replacement.

## Knowledge Packet

**Purpose:** Provide the only approved research input for content production.

**Owner:** Research Agent.

**Schema:** Topic, core question, definitions, canonical sources, contexts, misunderstandings, related concepts, confidence levels, citation requirements, editorial notes, risk flags.

**Quality Standard:** Complete, traceable, confidence-scored, risk-aware.

**Lifecycle:** Created per asset or anchor, versioned, updated when sources change.

## Episode Brief

**Purpose:** Define an asset's production intent without writing the content.

**Owner:** Planner Agent.

**Schema:** Asset function, audience, learning goal, viewer promise, format, pillar, series, concept nodes, emotional arc, dependencies, risk, deliverables.

**Quality Standard:** Specific, non-duplicative, aligned with architecture.

**Lifecycle:** Created after Knowledge Packet, revised before content creation if scope changes.

## Story Outline

**Purpose:** Define narrative beats, emotional progression, and structural movement.

**Owner:** Story Agent.

**Schema:** Arrival, recognition, orientation, tension, teaching, deepening, application, reflection, ending, callbacks, payoffs.

**Quality Standard:** Ethical curiosity, no fabricated material, clear arc.

**Lifecycle:** Created before full draft, revised through editorial review.

## Audio Script

**Purpose:** Provide final or draft spoken content for long-form video, audio essay, or podcast.

**Owner:** Writer Agent.

**Schema:** Sections, narration, pauses, pronunciation notes, source-sensitive lines, CTA, production notes.

**Quality Standard:** Accurate, natural spoken rhythm, TTS-friendly, compassionate, source-bounded.

**Lifecycle:** Drafted, reviewed, revised, approved, archived.

## Visual Brief

**Purpose:** Define the visual approach without creating final assets or prompts.

**Owner:** Visual Agent.

**Schema:** Visual intent, style, palette, lighting, character rules, environments, symbols, motion, accessibility, forbidden elements.

**Quality Standard:** Brand-aligned, visually clear, doctrinally respectful, accessible.

**Lifecycle:** Created after asset brief and content direction, revised through visual review.

**Purpose:** Define ethical thumbnail strategy and visual hierarchy.

**Owner:** Thumbnail Agent.

**Schema:** Subject, emotion, hierarchy, text-safe zone, color, contrast, series family, forbidden tactics, risk flags.

**Quality Standard:** Clear, compelling, non-clickbait, readable, brand-consistent.

**Lifecycle:** Created before thumbnail asset production, reviewed by visual and editorial gates.

## Image Prompt Package

**Purpose:** Provide controlled specification fields for image generation without treating prompt text as public content.

**Owner:** Visual Agent or AI Image Operator.

**Schema:** Purpose, subject, tradition context, environment, emotion, composition, lighting, palette, style, symbols, continuity, negative constraints, QA notes.

**Quality Standard:** Complete, model-independent, safe, reviewed.

**Lifecycle:** Generated from Visual Brief, versioned, archived with visual lineage. This document does not generate actual prompts.

## Voice Package

**Purpose:** Define audio performance requirements.

**Owner:** Content Agent and Audio Producer.

**Schema:** Voice tone, pacing, pronunciation, pauses, emotional notes, TTS handling, sacred term guidance, audio risk notes.

**Quality Standard:** Calm, reverent, clear, natural, accessible.

**Lifecycle:** Created before recording or synthesis, revised after audio QA.

## Editing Notes

**Purpose:** Guide video or audio assembly.

**Owner:** Producer or Editing Agent.

**Schema:** Sequence structure, pacing, visual timing, motion, transitions, music, silence, caption notes, accessibility notes.

**Quality Standard:** Supports teaching, avoids manipulation, preserves approved content.

**Lifecycle:** Created after script and visual brief, updated through edit review.

## Description

**Purpose:** Provide platform description, context, references, links, and viewer guidance.

**Owner:** SEO Agent and Metadata Agent.

**Schema:** Summary, context, references, playlist links, related assets, disclaimers where needed, chapters if applicable.

**Quality Standard:** Accurate, non-sensational, helpful, search-aware.

## SEO Package

# PART 7 - Workflow Orchestration

## Communication Model

Agents communicate through artifacts, not vague conversation. Each agent receives structured inputs and produces structured outputs. Comments, questions, and revision notes must be attached to artifact versions.

Communication rules:

**No agent should act on undocumented assumptions.**

**No agent should bypass required artifacts.**

**No agent should revise another agent's domain without recording changes.**

**Questions should be routed to the owning layer.**

**Escalations should include artifact ID and issue type.**

## Failure Propagation

Failures must propagate upstream. If the Writer Agent finds a missing claim, the issue returns to Research. If the Visual Agent finds that a scene requires historical reference, the issue returns to visual research. If SEO discovers search demand that requires a stronger promise than allowed, the issue returns to planning or is rejected.

Failures should not be patched downstream with improvisation.

## Retry Strategy

Retries must be specific. A retry should identify what failed and what must change.

Retry types:

**Research retry:** Missing evidence, weak source, unresolved conflict.

**Planning retry:** Scope too broad, duplication, wrong format.

**Content retry:** Unsupported claim, tone drift, structure failure.

**Visual retry:** Artifact, brand mismatch, sacred dignity failure.

**Metadata retry:** Missing taxonomy, broken links, wrong risk flags.

**Publishing retry:** File mismatch, platform error, incomplete package.

Retries must preserve version history.

## Rollback Strategy

Rollback returns production to a previous approved state.

Rollback is required when:

**A revision introduces unsupported claims.**

**A visual change violates dignity.**

**A metadata change breaks cross-links.**

**A publishing package uses wrong assets.**

**A source is deprecated before publication.**

Rollback should restore the last approved version and record the reason.

## Escalation

Escalation routes issues to appropriate authority:

**Research issue to Research Lead**

**Doctrine issue to Buddhist Reviewer**

**Translation issue to Translator**

**Safety issue to Safety Reviewer**

**Visual issue to Visual Director**

**Publishing issue to Publishing Lead**

**Archive issue to Knowledge Architect**

Escalation must be documented and blocking status identified.

## Checkpoint Validation

Checkpoints occur at gates. A checkpoint validates:

**Inputs complete**

**Outputs complete**

**Metadata complete**

**Versions correct**

**Dependencies satisfied**

**Risks addressed**

**Approvals recorded**

No stage should advance without checkpoint validation.

## Parallel Execution

Parallel execution is allowed only when dependencies are clear. For example, SEO intent mapping may begin after Asset Brief approval, while writing proceeds. Visual research may begin after Visual Brief scope is known. Metadata drafting may begin early.

Parallel work is not allowed when it depends on unapproved claims or unstable scope.

Parallel-safe tasks:

**Metadata draft after planning**

**Visual research after visual scope**

**SEO search intent after asset brief**

**Archive folder setup after project ID**

**Accessibility planning after format selection**

Parallel-unsafe tasks:

**Final thumbnail before content approval**

**Final description before claim review**

**Final visuals before sacred figure review**

**Publishing before package approval**

## Sequential Execution

Sequential execution is mandatory when one stage defines the truth conditions of the next.

Mandatory sequence:

**Research before writing**

**Knowledge Packet before Asset Brief finalization**

**Content approval before final publishing metadata**

**Visual approval before final thumbnail use**

**Publishing approval before distribution**

**Archive package after publication**

# PART 8 - Decision Engine

## Purpose

The Decision Engine teaches the Production Engine when to continue, stop, retry, reject, split, simplify, update, or escalate. It protects production from momentum.

## When to Stop

Stop production when:

**Required research is missing.**

**A high-risk topic lacks review.**

**The asset duplicates existing content without new function.**

**The claim exceeds evidence.**

**The visual direction violates dignity.**

**The package lacks required metadata.**

**The content creates safety risk.**

Stopping is not failure. It is system integrity.

## When to Retry

Retry when the issue is fixable within the same scope.

Retry examples:

**A draft has tone drift but research is sound.**

**A visual has AI artifacts but brief is correct.**

**Metadata is incomplete but asset is valid.**

**A description is too promotional but content is approved.**

Retry should not be used for fundamentally invalid topics.

## When to Reject

Reject when:

**The topic depends on forbidden claims.**

**Evidence cannot support the premise.**

**Safe framing is not possible.**

**The asset would exploit fear, grief, guilt, or illness.**

**The format is inappropriate for the topic.**

**The request violates governing documents.**

Reject with reason and archive the rejection to prevent repetition.

## When to Request More Research

Request more research when:

**A needed claim is absent from the packet.**

**Sources conflict.**

**Translation matters.**

**Historical detail is uncertain.**

**A reviewer asks for evidence.**

**The planned asset becomes higher-risk than expected.**

Do not let writing fill research gaps.

## When to Simplify

Simplify when:

**The asset has too many primary concepts.**

**The viewer level is beginner.**

**The format is short.**

**The emotional topic is heavy.**

**The evidence supports only a narrower claim.**

Simplification should preserve truth, not flatten doctrine.

## When to Split into Multiple Episodes

Split when:

**The asset has multiple core questions.**

**Several concepts require foundational explanation.**

**Sensitive topics need separate safety framing.**

**The story and doctrine compete for time.**

**The format would become too dense.**

Splitting creates better learning progression.

## When to Create a New Series

Create a new series only when:

**The viewer need is recurring.**

**The topic can sustain at least ten assets.**

**Existing series cannot contain it cleanly.**

**The series has distinct purpose and tone.**

**Architecture integration is possible.**

The Production Engine may recommend series creation but requires editorial approval.

## When to Update Existing Content

Update existing content when:

**A source changes.**

**A concept definition improves.**

**Viewer confusion repeats.**

**Visual standards improve.**

**A better anchor asset is created.**

**Metadata or links are outdated.**

Update rather than duplicate when the existing asset remains the right container.

# PART 9 - Editorial Governance

## Approval Hierarchy

Approval hierarchy defines who or what authority governs each domain.

**Research authority:** Research Lead and Research Engine.

**Doctrinal authority:** Buddhist Guide and qualified Buddhist Reviewer.

**Editorial authority:** Editorial Director and Brand Bible.

**Architecture authority:** Content Architecture and Knowledge Architect.

**Content authority:** Content Engine and Editorial Director.

**Visual authority:** Visual Engine and Visual Director.

**Safety authority:** Safety Reviewer for crisis, trauma, abuse, medical, children, and mental health.

**Publishing authority:** Publishing Lead and Production Engine.

No single authority can override all others. High-risk content requires domain-specific approval.

## Editorial Authority

Editorial authority governs topic fit, tone, viewer promise, series alignment, content structure, and final public meaning. It may reject content that is accurate but off-brand, emotionally unsafe, or not useful.

## Research Authority

Research authority governs evidence, confidence, source classification, citation, and uncertainty. Editorial teams cannot convert Low confidence into High confidence for narrative convenience.

## Visual Authority

Visual authority governs composition, style, imagery, sacred dignity, accessibility, and brand consistency. It cannot visually imply unsupported doctrinal claims.

## Doctrinal Authority

Doctrinal authority governs Buddhist meaning, tradition context, and sensitive teachings. It may block publication if content distorts karma, rebirth, ritual, merit, filial piety, sacred figures, or scripture.

## Version Approval

Approval applies to a specific version. If an artifact changes materially after approval, approval must be renewed. Minor typo fixes may be logged without full reapproval unless they affect meaning.

## Publishing Approval

Publishing approval confirms the complete package, not just the content. It includes files, metadata, links, thumbnail, references, captions, playlist placement, and archive readiness.

## Emergency Rollback

Emergency rollback is required when a published asset contains serious factual error, harmful language, wrong file, unsafe visual, broken attribution, or misleading metadata.

Rollback actions:

**Unpublish, private, or correct depending on severity.**

**Notify relevant leads.**

**Identify source of failure.**

**Correct archive and metadata.**

**Publish correction if appropriate.**

**Prevent recurrence.**

# PART 10 - Production QA Gates

## Gate Philosophy

QA gates are mandatory checkpoints. Each gate can produce pass, conditional pass, fail, retry, or escalation.

## Research Gate

**Pass:** Knowledge Packet complete, source-traceable, confidence-scored, risks flagged, escalation resolved.

**Conditional Pass:** Minor open issues do not affect public claims and are documented.

**Fail:** Missing sources, unverified quotes, unscored claims, unresolved high-risk concerns.

**Retry:** Return to Research Agent for additional evidence.

**Escalation:** Buddhist, translator, historical, or safety reviewer required.

## Planning Gate

**Pass:** Asset Brief aligned with architecture, non-duplicative, scoped, format-appropriate.

**Conditional Pass:** Minor metadata or dependency notes pending.

**Fail:** Vague scope, duplicate content, wrong format, missing viewer promise.

**Retry:** Planner revises.

**Escalation:** Editorial Director or Knowledge Architect.

## Content Gate

**Pass:** Content uses approved claims, fits voice, structure, emotional safety, and format.

**Conditional Pass:** Minor revisions required.

**Fail:** Unsupported claims, tone drift, fear language, doctrinal distortion, unsafe framing.

**Retry:** Writer or Story Agent revises.

**Escalation:** Research, doctrinal, editorial, or safety review.

## Visual Gate

**Pass:** Visual Brief or asset aligns with Visual Engine, brand, accessibility, and dignity.

**Conditional Pass:** Minor composition or technical fixes.

**Fail:** Fear visuals, sacred disrespect, AI artifacts, cultural inaccuracies, accessibility failure.

**Retry:** Visual Agent revises or recreates.

**Escalation:** Visual Director, Buddhist Reviewer, historical visual researcher.

## SEO Gate

**Pass:** SEO package improves discoverability without distortion.

**Conditional Pass:** Minor tag or description changes.

**Fail:** Clickbait, misleading title, fear keywords, miracle implication, unsupported promise.

**Retry:** SEO Agent revises.

**Escalation:** Editorial Director.

## Publishing Gate

**Pass:** Package complete, approved versions attached, metadata valid, links working.

**Conditional Pass:** Non-critical scheduling or platform detail pending.

**Fail:** Missing files, wrong versions, broken references, unapproved assets.

**Retry:** Publishing Agent corrects.

**Escalation:** Production Lead.

## Archive Gate

**Pass:** All artifacts stored, lineage recorded, metadata complete, reuse status set.

**Conditional Pass:** Minor analytics fields pending after release.

**Fail:** Missing source lineage, version history, approvals, or final files.

**Retry:** Archive Agent completes.

**Escalation:** Knowledge Architect.

# PART 17 - Production State Model

## Purpose

The Production State Model defines the official status of every production item. Without a state model, teams confuse drafts with approvals, stalled work with completed work, and published assets with archived assets. The state model makes the pipeline observable and auditable.

Every asset must have exactly one primary production state at a time. Substates may be used for detail, but the primary state determines what actions are allowed.

## State: Intake

**Definition:** A raw idea, request, seasonal need, analytics insight, or content gap has entered the system.

**Allowed Actions:** Clarify request, reject obvious violations, assign idea ID, prepare research request.

**Blocked Actions:** Writing, visual design, publishing package creation.

**Exit Criteria:** Research Request created or idea rejected.

## State: Researching

**Definition:** The asset is in the Research Layer.

**Allowed Actions:** Source collection, evidence matrix creation, confidence scoring, Knowledge Packet drafting, escalation.

**Blocked Actions:** Drafting public content, final title creation, final thumbnail planning.

**Exit Criteria:** Research Gate pass, conditional pass, or fail.

## State: Planning

**Definition:** Approved research is being transformed into an Asset Brief.

**Allowed Actions:** Architecture mapping, format selection, viewer journey definition, dependency mapping.

**Blocked Actions:** Final content creation, final visual creation.

**Exit Criteria:** Planning Gate pass.

## State: Drafting

**Definition:** Content artifacts are being created from the Asset Brief and Knowledge Packet.

**Allowed Actions:** Story outline, draft script, article draft, community post draft, course draft, podcast draft.

**Blocked Actions:** Publishing, final packaging, archive completion.

**Exit Criteria:** Content Gate pass or revision request.

## State: Visual Planning

**Definition:** Visual strategy is being defined.

**Allowed Actions:** Visual Brief, Thumbnail Brief, visual research request, series visual check, accessibility planning.

**Blocked Actions:** Final use of visual assets without Visual Gate.

**Exit Criteria:** Visual Planning Gate pass.

## State: Asset Production

**Definition:** Concrete media assets are being created or assembled from approved briefs.

**Allowed Actions:** Recording, editing, captioning, visual generation, motion design, thumbnail production, article formatting.

**Blocked Actions:** Distribution without approval.

**Exit Criteria:** Asset QA complete and ready for review.

## State: Review

**Definition:** Artifacts are being evaluated by required reviewers.

**Allowed Actions:** Research review, editorial review, doctrinal review, safety review, visual review, SEO review, QA review.

**Blocked Actions:** Publishing unless final approval has been granted.

**Exit Criteria:** Pass, conditional pass, fail, or escalation.

## State: Revision

**Definition:** One or more artifacts require changes based on review.

**Allowed Actions:** Revise within approved scope, request more research, update visual brief, correct metadata, rollback.

**Blocked Actions:** Advancing to publication until revision is reviewed.

**Exit Criteria:** Revised artifact passes relevant gate.

## State: Approved

**Definition:** All required artifacts have passed review.

**Allowed Actions:** Assemble publishing package, schedule distribution, prepare archive package.

**Blocked Actions:** Meaning-changing edits without reapproval.

**Exit Criteria:** Publishing Package complete.

## State: Scheduled

**Definition:** Publishing package is complete and assigned to a release time or distribution queue.

**Allowed Actions:** Final link check, platform readiness check, schedule confirmation.

**Blocked Actions:** Unreviewed changes.

**Exit Criteria:** Published or unscheduled due to issue.

## State: Published

**Definition:** The asset is publicly released.

**Allowed Actions:** Monitor performance, moderate comments, verify links, capture analytics baseline.

**Blocked Actions:** Silent replacement of major content without archive record.

**Exit Criteria:** Archive Gate and analytics follow-up.

## State: Archived

**Definition:** The asset and its lineage are preserved.

**Allowed Actions:** Maintenance, updates, reuse, analytics review, deprecation if needed.

**Blocked Actions:** Loss of lineage or untracked reuse.

**Exit Criteria:** Asset remains current, updated, deprecated, or replaced.

## State: Deprecated

**Definition:** The asset is no longer recommended as the best current version.

**Allowed Actions:** Redirect, update description, create replacement, archive status update.

**Blocked Actions:** Presenting as current anchor content.

**Exit Criteria:** Replaced, corrected, or permanently archived.

## State: Rejected

**Definition:** The request or asset cannot proceed.

**Allowed Actions:** Record reason, preserve rejection note, prevent repeated attempt.

**Blocked Actions:** Restarting without new evidence or scope change.

**Exit Criteria:** None unless reopened through approved review.

# PART 28 - Production Readiness Model

## Purpose of Readiness

Production readiness is the studio's disciplined answer to a simple question: is this work actually prepared to enter the next stage, or is it merely present in the folder? A long-running Buddhist channel cannot rely on enthusiasm, urgency, or surface polish as evidence of readiness. Readiness must be defined through observable conditions. The Production Engine therefore treats every artifact as unready until it satisfies the readiness criteria for its current stage.

Readiness is not perfection. Perfectionism can paralyze production and create hidden quality debt. Readiness means that the artifact contains enough verified, structured, and governed information for the next responsible agent to perform its work without guessing. A research brief is ready when a writer can identify sources, claims, uncertainties, doctrinal boundaries, and intended teaching function. A script is ready when a reviewer can evaluate it against doctrine, brand, narrative, and safety standards. A publishing package is ready when a publishing operator can schedule and release it without inventing missing information.

The canonical studio rule is: **no stage may accept an artifact whose readiness cannot be demonstrated.** This rule protects the channel from rushed production, silent hallucination, and inconsistent execution across hundreds of videos.

## Readiness Is Stage-Specific

Every production stage has its own readiness definition. The studio must not use one generic definition of readiness for all work. A concept can be ready for research while being completely unready for writing. A script can be ready for doctrinal review while being unready for visual planning. A visual package can be ready for internal review while being unready for publication.

The Production Engine must record readiness by stage, not by general status. A single yes-or-no label such as "ready" is insufficient. The required status must identify the next destination: ready for research, ready for planning, ready for scripting, ready for review, ready for revision, ready for publishing, ready for archive, or ready for maintenance.

This distinction matters because it prevents premature escalation. A partially researched topic should not reach the writing agent just because someone wants momentum. A script that has not passed Buddhist Editorial QA should not reach visual production just because the schedule is tight. A publishing package that lacks archive metadata should not be released just because the video file exists.

## Intake Readiness

An item is ready for intake only when it has a defined production identity. The system must know whether the item is a new topic request, a continuation of an existing series, a revision of prior work, a response to audience feedback, a seasonal or commemorative production, or a maintenance update. The intake record must include enough context to determine which governing documents apply and which risk class is likely.

Intake readiness requires a working title, proposed content category, intended audience need, preliminary risk assessment, and relationship to existing channel architecture. If the item belongs to an established series, the series identity must be named. If it may create a new series, it must be routed through architecture review before any downstream work begins.

The intake stage must not approve vague items such as "make something about karma" or "do a healing video." Such requests may be stored as raw signals, but they are not ready for production. They must be converted into a governed production request before entering the pipeline.

## Research Readiness

An item is ready for research when the research purpose is specific enough to guide source gathering. The Production Engine must define what the research agent is expected to clarify: scripture meaning, doctrinal interpretation, historical context, terminology, audience sensitivity, comparative interpretation, risk boundaries, or prior channel continuity.

Research readiness requires a research scope, accepted source categories, prohibited source categories, citation expectations, uncertainty areas, and escalation triggers. For high-risk topics, the research request must include the relevant rules from the Buddhist Guide and Research Engine. If the topic touches death, grief, rebirth, hell realms, family trauma, suicide, illness, mental health, miracles, historical claims, or sectarian difference, the research request must explicitly identify the risk.

No research task should begin from a purely creative prompt. Research begins from a governed question. The research agent must never be asked to "find inspiring material" without doctrinal and factual boundaries. Inspiration is a later editorial function; research is the function of evidence, clarity, and responsible framing.

## Planning Readiness

An item is ready for planning when the research base has enough structure for a content architect to determine format, series placement, teaching sequence, and viewer journey. Planning must not begin from raw source dumps. The research brief must identify primary claims, interpretive boundaries, unresolved uncertainties, audience sensitivities, and approved terminology.

Planning readiness requires a completed research brief, source confidence rating, risk classification, intended content pillar, proposed format category, and continuity check against existing series. The planning agent must also receive any required doctrinal cautions. If a topic has multiple valid interpretations, planning must receive an interpretation map rather than a single flattened conclusion.

The planner may reject an item as not ready if the research brief lacks citation lineage, obscures uncertainty, overstates certainty, or fails to distinguish scripture, commentary, tradition, legend, and modern reflection. This rejection is not a production failure. It is the system operating correctly.

## Writing Readiness

An item is ready for writing only when the writing agent receives a complete creative and editorial brief. The brief must identify the approved angle, intended emotional journey, teaching boundaries, narrative posture, allowed vocabulary, forbidden language, source references, and required disclaimers or careful phrasing.

Writing readiness does not mean that the script has been imagined. It means that the writer has enough constraints to write consistently within the channel's system. Future AI writers must never receive a naked instruction such as "write a video about the Diamond Sutra." The Production Engine must supply the necessary context from the PRD, Brand Bible, Buddhist Guide, Content Architecture, Content Engine, and Research Engine.

The writing stage must not accept items with unresolved doctrine risk unless the brief explicitly instructs the writer how to handle uncertainty. Silence is not permission. If the source record says "uncertain," the writing brief must say whether to omit, qualify, escalate, or present multiple interpretations with humility.

## Review Readiness

An artifact is ready for review when it is complete enough to be judged against standards. Fragmentary work may be discussed informally, but it must not enter formal review. Formal review requires stable pagination or section identifiers, version number, source package, intended use, and reviewer assignment.

Review readiness also requires the artifact to declare what kind of review it needs. Buddhist doctrinal review, brand review, narrative review, psychological safety review, historical review, scientific integrity review, visual dignity review, publishing review, and accessibility review are not interchangeable. A script that passes brand review may still fail doctrinal review. A thumbnail concept that passes visual impact review may still fail Buddhist dignity review. A metadata package that passes SEO review may still fail truthfulness review.

The Production Engine must prevent review collapse, where one reviewer or one automated pass is treated as sufficient for all dimensions. Review must be modular, documented, and accountable.

## Publishing Readiness

A production package is ready for publishing only when all required artifacts are present, all gates are passed, and all metadata is archived. The existence of a final video file is not enough. Publishing readiness includes final title approval, description approval, source transparency notes if needed, thumbnail approval, audio quality check, caption or transcript status, age or sensitivity guidance if relevant, upload configuration, release timing, archive destination, and post-publication monitoring plan.

Publishing readiness must include a final ethics check. The studio must ask whether the release creates spiritual pressure, exaggerated promise, medical implication, fear-based motivation, or disrespectful representation. If any such risk appears, the package must return to review.

For high-risk topics, publishing readiness also requires human signoff. The Production Engine must not permit an automated system to self-authorize publication where the Buddhist Guide or Research Engine requires escalation.

## Archive Readiness

An item is ready for archive when it can be recovered, audited, revised, and understood by someone who did not participate in the original production. Archive readiness requires final artifacts, source artifacts, approval records, version history, decision logs, risk classification, release metadata, performance summary, and maintenance notes.

The archive must not store only polished outputs. It must store the reasoning trail that allows future teams to understand why the episode exists, what interpretation was chosen, what sources were used, what risks were considered, and what decisions were made. Without that record, future production teams may unknowingly contradict earlier work or repeat avoidable mistakes.

Archive readiness also includes discoverability. Artifacts must use canonical naming, stable IDs, and metadata fields defined by the Production Engine. A document that exists but cannot be found is operationally equivalent to a missing document.

## Maintenance Readiness

A published item is ready for maintenance review when there is a defined reason to revisit it. Reasons include discovered factual error, doctrinal concern, viewer confusion, outdated language, improved source availability, brand evolution, accessibility need, platform policy change, or performance anomaly that suggests misunderstanding.

Maintenance readiness requires a maintenance trigger, the affected artifact list, severity rating, proposed review scope, and rollback or correction options. The Production Engine must distinguish between optimization and correction. Optimization seeks better performance while preserving integrity. Correction addresses a meaningful defect. A correction must be handled with transparency and humility.

The channel must not quietly rewrite its own history in ways that obscure mistakes. If a meaningful public error occurred, the correction record must preserve what changed and why.

# PART 29 - Multi-Year Continuity System

## Continuity as a Product Requirement

A channel designed to publish hundreds of Buddhist videos over many years must treat continuity as a product requirement, not an aesthetic preference. Viewers should feel that every video belongs to the same moral, educational, and cinematic world even when topics differ widely. A video on the Lotus Sutra, a meditation reflection, a story of a Bodhisattva, a teaching on filial piety, and a modern reflection on grief may vary in structure, but they must share a recognizable standard of reverence, clarity, restraint, and compassion.

The Production Engine is responsible for protecting continuity across time. It must ensure that future agents inherit the channel's accumulated decisions rather than repeatedly rediscovering them. Continuity must be stored in systems, not in individual memory.

## Continuity Dimensions

The studio must preserve continuity across at least nine dimensions: doctrinal continuity, terminology continuity, brand voice continuity, narrative continuity, visual continuity, music continuity, editorial risk continuity, audience promise continuity, and archive continuity.

Doctrinal continuity means that core Buddhist teachings are explained with stable humility and without contradiction. Terminology continuity means that key terms such as karma, merit, rebirth, compassion, emptiness, mindfulness, filial piety, Bodhisattva, Buddha, and liberation are handled consistently. Brand voice continuity means that the channel maintains a calm, respectful, cinematic, reflective tone. Narrative continuity means that stories and teachings follow the same principles of emotional pacing and transformation. Visual continuity means that imagery remains dignified, coherent, and non-sensational. Music continuity means that sound supports reverence rather than manipulation. Editorial risk continuity means that sensitive subjects receive the same care over time. Audience promise continuity means that viewers know what kind of refuge and learning experience they can expect. Archive continuity means that all production records remain recoverable.

No single episode should redefine any of these dimensions without formal governance.

## Continuity Ledger

The studio must maintain a Continuity Ledger as a permanent operating artifact. The ledger records decisions that affect future production. It is not a content calendar and not a creative scrapbook. It is a governance record.

The Continuity Ledger should include approved terminology, rejected terminology, recurring phrasing principles, canonical title patterns, recurring visual rules, recurring music rules, doctrinal interpretation decisions, high-risk topic precedents, correction history, audience feedback patterns, and approved exceptions.

When a new decision changes how future work should be produced, it must be entered into the ledger. For example, if reviewers determine that a specific phrase about karma creates blame toward suffering people, that phrase and its replacement principle must be recorded. If a visual treatment of hell realms is approved as symbolic rather than graphic, the decision must be recorded. If a series establishes a canonical naming pattern, the pattern must be recorded.

The ledger prevents the studio from treating each episode as an isolated creative act.

## Continuity Reviews

The studio must conduct continuity reviews at scheduled intervals. A continuity review examines whether recent productions still align with the governing documents. It does not begin by asking what performed best. It begins by asking whether the channel remains itself.

The review must sample published work across different content pillars and examine voice, doctrine, visual language, titles, emotional tone, claims, and audience response. Any drift must be classified as acceptable evolution, correctable inconsistency, serious risk, or strategic concern.

Acceptable evolution may include refined production values, clearer explanations, or more mature pacing. Correctable inconsistency may include small terminology variations, uneven title tone, or inconsistent description formatting. Serious risk may include doctrinal overstatement, fear-based language, implied medical promise, or visual sensationalism. Strategic concern may include audience confusion about the channel's identity or a content pillar pulling the brand away from its core purpose.

Continuity review results must feed into future briefs, not remain as retrospective commentary.

## Canonical Memory vs Temporary Memory

The Production Engine must distinguish canonical memory from temporary memory. Canonical memory includes permanent standards, approved exceptions, correction decisions, terminology rules, and production architecture. Temporary memory includes current campaign notes, one-off workflow constraints, seasonal scheduling, unfinished experiments, and short-term analytics observations.

Only canonical memory may govern future production by default. Temporary memory may inform current work but must expire unless formally promoted. This distinction prevents a short-term experiment from becoming an accidental permanent rule.

To promote temporary memory into canonical memory, the studio must record the reason, evidence, reviewer approval, affected documents, and revision date. A passing trend, one successful episode, or one viewer comment is not enough.

## Series Continuity

Each series must maintain its own continuity record. The record must include series purpose, audience need, teaching territory, tone boundaries, naming structure, visual identity within the master brand, episode structure rules, source expectations, high-risk areas, and known viewer responses.

When a new episode enters an established series, the Production Engine must attach the series continuity record to the production package. The agent working on that episode must not reconstruct the series identity from memory. If the episode requires deviation from series norms, the deviation must be approved and logged.

Series continuity records must remain subordinate to the master governing documents. A series cannot develop a voice, visual identity, or doctrinal posture that contradicts the Brand Bible or Buddhist Guide.

## Topic Continuity

Some topics will recur across many series. Karma may appear in scripture explanation, family ethics, grief reflection, Buddhist psychology, and stories from the life of the Buddha. Compassion may appear in meditation, Bodhisattva teachings, social conflict, and healing. Rebirth may appear in sutra interpretation, death education, and devotional practice.

The Production Engine must maintain topic continuity notes for recurring high-importance concepts. These notes should identify canonical explanation boundaries, phrases to avoid, common misunderstandings, approved analogies, source anchors, and escalation conditions.

Topic continuity prevents the channel from explaining the same concept differently in ways that confuse viewers. It also allows the channel to deepen understanding over time without contradiction. A beginner video may explain karma simply, while an advanced video may address complexity, but both must share the same ethical foundation.

## Continuity During Team Changes

The channel must assume that writers, editors, researchers, producers, and AI systems will change over time. Continuity cannot depend on a single founding team. Every role must be able to onboard through documents, artifacts, examples, and checklists.

When a new agent enters the production system, the Production Engine must provide the governing hierarchy, relevant series continuity record, relevant topic continuity notes, current risk rules, current naming rules, and archive access. The agent must pass a readiness check before producing publishable work.

If a new agent produces output that conflicts with the channel identity, the failure must be treated as either an onboarding gap, a brief gap, a governance gap, or an execution gap. The studio must identify the true cause rather than simply rejecting the output.

## Continuity During Platform Change

Platforms change formats, policies, recommendation systems, metadata fields, and viewer behavior. The channel may adapt to these changes, but adaptation must not weaken core standards. If short-form, long-form, audio-only, live, community post, newsletter, course, or documentary formats are adopted, the Production Engine must translate existing brand and Buddhist standards into the new format.

No platform feature may become an excuse for sensational language, manipulative urgency, doctrine oversimplification, or visual disrespect. The channel may become more accessible, but not less careful. It may become more efficient, but not less traceable. It may become more cinematic, but not less honest.

## Continuity as Viewer Trust

For viewers, continuity becomes trust. They may not know the names of the governing documents, but they will feel whether the channel remains steady. A channel that changes voice, claims, visual tone, and emotional posture every few months trains viewers to distrust it. A channel that remains recognizably compassionate, honest, and beautiful becomes a dependable presence.

The Production Engine must therefore treat continuity not as internal bureaucracy but as part of the viewer experience. The viewer should feel that the channel is a place where Buddhist wisdom is handled with care every time.

# PART 30 - Quality Debt Management

## Definition of Quality Debt

Quality debt is any production compromise that creates future cost, confusion, risk, or inconsistency. It may be visible or invisible. Visible quality debt includes poor audio, inconsistent thumbnails, unclear titles, weak pacing, or missing captions. Invisible quality debt includes weak source records, undocumented decisions, unreviewed doctrinal claims, unclear version history, undocumented exceptions, and missing archive metadata.

The Production Engine must treat quality debt as a measurable operational condition. It must not be hidden under the language of speed, experimentation, or platform pressure. Some debt may be temporarily accepted, but it must be named, logged, owned, and resolved.

Quality debt is not moral failure. It is a production reality. The risk comes from pretending it does not exist.

## Types of Quality Debt

The studio must classify quality debt into categories. Doctrinal debt includes unclear Buddhist interpretation, weak scripture citation, unresolved tradition differences, or imprecise language around karma, rebirth, merit, emptiness, compassion, or liberation. Editorial debt includes inconsistent voice, weak structure, inflated claims, unclear audience promise, or unapproved deviation from brand standards. Research debt includes insufficient sources, missing citations, weak source hierarchy, unclear uncertainty notes, or reliance on secondary material where primary or authoritative sources are needed.

Visual debt includes inconsistent style, disrespectful imagery, unclear symbolic logic, poor composition, or asset metadata gaps. Audio debt includes poor mixing, intrusive music, emotional manipulation, or inconsistent sonic identity. Publishing debt includes incomplete descriptions, weak correction notes, missing accessibility artifacts, inconsistent metadata, or poor archive linkage. Operational debt includes missing handoff notes, unclear approvals, untracked versions, undocumented exceptions, and unmanaged backlogs.

Each debt type requires a different remedy. The Production Engine must not solve all quality debt with generic revision.

## Debt Severity

Quality debt must be assigned severity. Low debt creates inconvenience but not meaningful risk. Medium debt affects consistency, clarity, or viewer experience. High debt creates doctrinal, safety, historical, scientific, ethical, or trust risk. Critical debt may require stopping publication, correcting published material, or escalating to human leadership.

Low debt may be scheduled for routine improvement. Medium debt requires assignment and due date. High debt blocks publishing unless explicitly waived by appropriate human authority. Critical debt triggers immediate escalation and potential pause.

No AI agent may downgrade a debt severity for convenience. Downgrading requires evidence and, for high-risk categories, human approval.

## Debt Register

The studio must maintain a Quality Debt Register. Every accepted compromise must be logged with artifact ID, debt category, severity, owner, reason accepted, expected impact, resolution plan, due date, and final disposition. The register makes quality debt visible and prevents it from becoming normal.

The register must include both pre-publication and post-publication debt. If a published video has missing archive metadata, that is debt. If a series has inconsistent naming across early episodes, that is debt. If old videos use language that later standards reject, that is debt requiring maintenance classification.

The register must be reviewed regularly by production leadership. Patterns matter more than individual items. Repeated debt in the same category signals a system flaw.

## Acceptable Temporary Debt

Temporary quality debt may be accepted only when it does not violate core Buddhist, safety, ethical, or trust standards. For example, a minor formatting inconsistency in an internal artifact may be accepted temporarily if it does not affect publication quality or future auditability. A non-critical archive field may be filled after publication if the production package remains recoverable.

Temporary debt must never include unverified doctrinal claims, unsafe mental health language, manipulative fear appeals, fabricated citations, misleading historical certainty, disrespectful visuals, or unreviewed high-risk content. These are not acceptable debt. They are blockers.

## Debt Repayment

Debt repayment must be scheduled as production work. It cannot be left to vague future goodwill. The Production Engine must allocate maintenance capacity for corrections, archive cleanup, metadata normalization, accessibility improvements, and standard updates.

Debt repayment should prioritize high-risk and high-reuse assets. A terminology error in a core guide affects many future productions and must be repaired before minor cosmetic inconsistencies. A missing citation in a foundational scripture explanation is more urgent than a low-impact visual alignment issue.

Repayment must include root cause analysis. If a citation was missing, the question is not only "how do we add it?" The question is "why did the system allow the artifact to move forward without it?"

## Debt Prevention

The best debt system prevents avoidable debt. Prevention includes clear input contracts, mandatory gates, template use, reviewer assignment, artifact schemas, naming standards, source requirements, and archive discipline.

The Production Engine must identify recurring debt and convert prevention into workflow rules. If scripts often arrive without uncertainty language, the writing brief template must be updated. If visual packages frequently miss asset provenance, the visual handoff contract must be strengthened. If metadata often becomes sensational during final optimization, publishing QA must include a stronger truthfulness check.

Debt prevention is a design function, not a scolding function.

## Legacy Debt

As the channel matures, early productions may fall below later standards. This is normal. The Production Engine must manage legacy debt with humility. Older work should not be erased simply because standards improved. It should be reviewed, classified, corrected when necessary, and contextualized when appropriate.

Legacy debt review should prioritize videos that continue receiving traffic, videos on high-risk topics, foundational series, and videos frequently referenced by newer content. Low-traffic low-risk legacy items may be scheduled later.

The studio must avoid two extremes: treating old work as untouchable because it is published, or constantly revising everything so aggressively that the channel loses productive capacity. Legacy maintenance must be deliberate.

# PART 31 - Channel Operating Memory

## Purpose of Operating Memory

Operating memory is the studio's structured knowledge of how the channel actually functions over time. It is broader than the archive and more actionable than analytics. It includes decisions, lessons, exceptions, viewer misunderstandings, review patterns, production bottlenecks, successful standards, failed experiments, and unresolved questions.

The Production Engine must ensure that operating memory is captured, curated, and made usable. Without operating memory, the channel repeats the same debates, recreates the same errors, and loses the benefit of experience. With operating memory, each production cycle makes the studio wiser.

Operating memory must remain humble. It does not replace scripture, scholarship, or governing documents. It records how the studio has applied them.

## Memory Categories

The studio must classify operating memory into categories: doctrinal application memory, editorial memory, audience memory, visual memory, audio memory, workflow memory, risk memory, correction memory, and strategy memory.

Doctrinal application memory records how the studio has handled recurring Buddhist concepts and interpretive tensions. Editorial memory records voice decisions, narrative lessons, pacing observations, and language patterns. Audience memory records recurring viewer questions, confusion points, appreciation patterns, and sensitivity concerns. Visual memory records approved and rejected image treatments, symbolic rules, and dignity precedents. Audio memory records music and sound decisions that support or weaken the desired experience. Workflow memory records handoff failures, bottlenecks, and operational improvements. Risk memory records topics that required escalation and how they were resolved. Correction memory records errors and remedies. Strategy memory records long-term positioning decisions.

Each category must be searchable and linked to the artifacts that produced it.

## Memory Capture Points

Operating memory must be captured at defined points, not only when someone remembers. Required capture points include post-research review, post-script review, post-visual review, post-publication monitoring, monthly production review, quarterly continuity review, correction events, major audience feedback events, and governance updates.

At each capture point, the responsible producer must ask what the studio learned that should affect future work. Most productions will yield small lessons. Some will yield none. A few will yield major governance changes. The system must allow all three outcomes.

The capture format should be concise. Operating memory fails when it becomes too burdensome to maintain. Each entry should identify the lesson, evidence, affected standards, affected future workflows, and review date.

## Memory Promotion

Not every lesson becomes a rule. The Production Engine must provide a promotion path from observation to guideline to standard. An observation is a single noted event. A guideline is a repeated or reviewed pattern that may inform future work. A standard is a binding rule added to governing documents or continuity records.

Promotion requires evidence and editorial judgment. One comment from a viewer does not automatically change the channel's voice. One successful title does not redefine naming rules. One production difficulty does not justify a new bureaucracy. The studio must look for patterns, risks, and alignment with core purpose.

When a memory item is promoted, the promotion record must identify which documents or templates change. If no document changes, the item remains advisory.

## Memory Retirement

Operating memory can become outdated. A platform behavior may change. A production tool may be replaced. A viewer misunderstanding may be resolved by better explanation. A visual rule may become unnecessary after the Visual Engine evolves.

The Production Engine must allow memory retirement. Retired items must not be deleted without record. They should be marked inactive with a reason and date. This preserves institutional history while preventing obsolete guidance from confusing future agents.

Memory retirement is especially important for AI systems. Old constraints can accumulate and conflict unless curated. The channel must avoid becoming governed by fossilized exceptions.

## Memory Access

Future AI agents must receive the operating memory relevant to their task. They should not be given the entire memory archive indiscriminately if only a narrow subset applies. Excess context can dilute priority and increase contradiction risk.

The Production Engine must route memory by role, topic, series, risk class, and production stage. A visual agent needs visual memory and symbolic precedents. A research agent needs doctrinal application memory and source precedents. A publishing agent needs title, description, metadata, correction, and audience memory.

Memory access must include version date. Agents must know whether the memory item is current, retired, experimental, or under review.

## Memory Integrity

Operating memory must be protected from casual opinion. Personal taste, momentary frustration, or isolated preference must not be recorded as authoritative memory. The system should require evidence labels: reviewer observation, audience data, correction record, source update, production bottleneck, governance decision, or strategic decision.

Memory entries must avoid vague claims such as "people like this tone" or "this topic always performs well." They must state what was observed, in what context, and how confidently the studio should treat it.

The studio must also protect memory from analytics absolutism. A video's performance may provide useful signals, but it does not automatically validate its editorial choices. A high-performing video may still contain problems. A low-performing video may still be excellent and necessary.
